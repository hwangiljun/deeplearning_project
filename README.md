# NextPitch — 상황 인식형 트랜스포머 기반 투구 전략 분석

MLB Statcast 투구 단위 데이터로 **다음 공의 결과를 예측**하고, 그 확률 분포를
**기대 실점으로 환산해 가장 유리한 구종과 코스를 제시**하는 시스템.
분석 결과는 Streamlit 대시보드로 제공한다.

```bash
pip install -r requirements.txt
streamlit run app.py
```

---

## 왜 만들었나

야구 분석의 전통적 지표 — 타율, 출루율, OPS — 는 선수의 **전반적 가치**를 요약한다.
하지만 마운드 위의 투수와 포수가 실제로 필요로 하는 건 다른 종류의 정보다.

> *2사 만루, 볼카운트 2-2, 상대는 좌타 거포.
> 지금 무슨 공을 어디에 던져야 하는가?*

누적 지표는 이 질문에 답하지 못한다. **결과를 요약할 뿐 선택을 돕지 않기 때문**이다.
같은 슬라이더라도 0-0에 던질 때와 3-2에 던질 때의 의미가 다르고, 같은 코스라도
직전에 무슨 공을 보여줬는지에 따라 타자의 반응이 달라진다.

이 프로젝트는 그 간극을 메우려는 시도다. 투구 하나하나를 **의사결정 문제**로 다루고,
"이 공을 던지면 어떤 일이 얼마의 확률로 일어나고, 그것이 실점 기대값을 얼마나
바꾸는가"를 계산한다.

### 설계 목표

| | |
|---|---|
| **상황을 반영할 것** | 카운트·주자·아웃·이닝·점수차가 예측에 실제로 들어가야 한다 |
| **확률이 정직할 것** | 후보를 확률로 순위화하므로, 표시되는 확률이 실제 빈도와 맞아야 한다 |
| **해석 가능할 것** | 점수의 단위가 '실점'이어서 "이 공이 0.03점 유리하다"로 읽혀야 한다 |
| **현장에서 쓸 수 있을 것** | 존 밖 유인구를 포함하고, 투수의 제구 수준을 감안해야 한다 |

## 데이터

Statcast 2024·2025 정규시즌 전체를 `pybaseball` 로 수집한다.

**샘플 단위는 투구 하나**다. 각 투구를 타깃으로 삼고, 같은 타석에서 그보다 앞서
던져진 공들을 최대 6구까지 앞에 붙여 시퀀스를 만든다. 시퀀스는 **타석 경계를
넘지 않는다** — 다른 타자·투수의 공이 한 시퀀스에 섞이지 않는다. 타석당 평균
투구 수가 3.82구이고 91.7%의 타석이 6구 이하이므로, 길이 6은 대부분의 타석을
온전히 포괄한다.

좌표는 타자 기준으로 정규화한다.

- **좌타자는 좌우를 미러링** — 좌우 타자를 같은 의미 축에서 비교할 수 있다
- **높이는 타자별 스트라이크존으로 정규화** — 신장 차이를 흡수한다
- **회전축은 sin·cos로 분해** — 0도와 359도가 인접하도록

### 입력 변수

| 경로 | 변수 | 개수 |
|---|---|---|
| 시퀀스 (물리량) | 좌우 위치, 정규화 높이, 구속, 회전수, 회전축(sin·cos), 수평·수직 무브먼트 | 8 |
| 시퀀스 (범주형) | 타자, 투수, 구종, 타석 좌우, 투구 좌우 | 5 |
| 맥락 | 볼, 스트라이크, 아웃, 주자 1·2·3루, 이닝, 초말, 점수차, 타순 회차 | 10 |
| 맥락 (타자 특성) | 직전 시즌 삼진율, 홈런율, ISO, 타율, OPS | 5 |

타자 특성은 **직전 시즌** 성적만 쓴다. 같은 시즌 성적을 그 시즌 예측에 넣으면
누수가 된다.

### 출력 클래스

```
ball · called_strike · swinging_strike · foul · hit_by_pitch
field_out · single · double · triple · home_run
```

`strikeout` / `walk` 는 클래스에 넣지 않는다. 삼진은 2스트라이크에서의 스트라이크,
볼넷은 3볼에서의 볼이므로 **투구의 결과가 아니라 카운트에서 파생되는 타석 결과**다.
카운트가 이미 입력에 있는 상태에서 이를 별도 클래스로 두면 모델이 공짜로 맞히는
라벨이 생긴다. 두 사건은 예측된 클래스와 현재 카운트로부터 결정적으로 유도한다.

## 모델

시퀀스와 맥락을 **별도 경로로 처리한 뒤 출력 직전에 결합**하는 이원 구조다.
같은 구조를 Takamido & Nakamoto (2026) 도 독립적으로 채택했다.

```
투구 시퀀스 (타석 내 최근 6구)
  │
  ├─ 엔티티 임베딩 (타자·투수·구종·좌우)  ┐
  ├─ 물리량 8개                          ┴─→ 선형 사영 + 위치 임베딩 (d=128)
  │                                              │
  │                                     Transformer Encoder (2층, 4헤드, FFN 512)
  │                                              │
  │                                       마스크드 평균 풀링
  │                                              │
맥락 15개 ─→ Dense + ReLU (32) ──────────────────┤  ← 스킵 연결
                                                 │
                                        결합 (128+32=160)
                                                 │
                                     MLP → 10 클래스 + 기대실점 회귀
```

**486,199 파라미터 / 2.0MB.**

### 왜 이 구조인가

**엔티티 임베딩** — 타자·투수·구종처럼 값의 종류가 많은 범주형 변수를 학습 가능한
밀집 벡터로 사상한다. 원-핫과 달리 선수 간 유사성이 벡터 공간에 표현될 수 있다.
인덱스 0은 **UNK(미등록 선수)** 로 예약하고, 학습 중 일정 확률로 선수 ID를 UNK로
치환해 그 임베딩이 실제로 훈련되게 한다. 처음 보는 선수가 들어와도 무너지지 않는다.

**Transformer 인코더** — 셀프 어텐션으로 타석 내 투구 간 관계를 학습한다.
Pre-LN 구성이므로 **최종 LayerNorm** 을 반드시 붙이고, 타석 앞부분 패딩에는
**어텐션이 걸리지 않도록 마스크**를 씌운다. 마지막 토큰만 쓰는 대신
**유효 구간 평균 풀링**을 써서 짧은 타석에서도 안정적으로 동작하게 했다.
레이어 수는 2층인데, 이는 Takamido & Nakamoto 의 하이퍼파라미터 탐색 결과와도 일치한다.

**맥락 경로와 스킵 연결** — 현재 상황 정보를 어텐션에 통과시키지 않고 출력층에
직접 연결한다. 긴 시퀀스 처리 과정에서 '당면한 위기 상황'이 희석되는 것을 막기
위해서다. **이 경로가 이 프로젝트의 핵심 가설이며, 어블레이션에서 실제로 기여가
확인된 유일한 구성요소다.**

**출력 헤드** — BatchNorm 대신 LayerNorm을 쓴다. BatchNorm은 배치 구성에 민감해
추론 시 배치 크기가 달라지는 응용 환경에 맞지 않는다. 분류 헤드와 별도로
기대 득점 변화량을 직접 예측하는 보조 회귀 헤드를 함께 학습한다.

### 학습

2024 시즌 학습 / **2025 시즌 테스트**. 검증셋은 학습 구간의 **뒷부분 날짜**에서
15%를 뗀다. 인코더와 정규화 통계는 학습 구간에만 적합한다.

손실은 단순 교차 엔트로피이고 **오버샘플링을 쓰지 않는다.** 불균형 보정은
희귀 클래스 재현율을 올리는 대신 출력 확률을 실제 분포에서 밀어낸다. 이 시스템은
확률을 적분해 후보를 고르므로 **정직한 확률이 높은 재현율보다 중요하다.**
조기 종료 기준은 정확도가 아니라 **검증 log-loss** 다.

## 추천 로직

후보는 **해당 투수가 실제로 던지는 구종** × **9×9 좌표 격자**로 생성한다.
격자는 스트라이크존 밖까지 덮으므로 유인구도 후보에 들어온다. 각 구종의 물리량은
리그 평균 상수가 아니라 **그 투수의 실측 평균**을 쓴다 (투수 1,010명 / 3,950개
(투수, 구종) 조합).

점수는 결과 확률을 카운트 조건부 기대 실점으로 가중합한 값이다.

```
score(p) = Σ_c  P(결과 = c | 투구 p, 상황) × ΔRE(c | 볼카운트)
```

`ΔRE` 는 Statcast 의 투구별 기대 득점 변화량(`delta_run_exp`)에서 직접 추정한다.
같은 사건도 카운트에 따라 가치가 크게 달라진다.

| 결과 | 0-0 | 0-2 | 3-2 |
|---|---|---|---|
| ball | +0.035 | +0.021 | **+0.287** |
| called_strike | −0.040 | −0.168 | **−0.323** |
| foul | −0.040 | **−0.010** | −0.018 |
| field_out | −0.253 | −0.166 | −0.319 |

3-2의 볼은 볼넷이라 0-0의 볼보다 8배 나쁘고, 2스트라이크의 파울은 거의 무가치하다.
단위가 실점이므로 추천 결과를 **"이 공을 던지면 기대 실점이 0.03 줄어든다"** 로
읽을 수 있다.

마지막으로 **command window** 를 적용한다. 투수는 한 점을 정확히 겨눌 수 없으므로,
노린 지점 주변 윈도우의 평균을 그 지점의 대표값으로 삼는다. 윈도우 크기를 바꾸면
제구가 정밀한 투수와 그렇지 않은 투수를 구분해 평가할 수 있다.

## 결과

2024 시즌 학습 / **2025 시즌 712,516구 홀드아웃** (학습·조기종료·모델선택에 미사용).

| 지표 | 값 |
|---|---|
| log-loss | **1.1259** |
| macro AUC | **0.8410** |
| ECE | **0.0084** |
| macro F1 | 0.2633 |
| 정확도 | 57.48% |

### 확률이 정직하다

검증셋에서 적합한 temperature 가 **1.070** 으로 1에 근접한다. 이는 모델이 이미
보정되어 있어 **추가 보정이 필요 없다**는 뜻이다. 실제로 적용해도 log-loss 는
1.1259 → 1.1248 로 거의 변하지 않는다. 화면에 뜨는 확률이 실제 빈도와 일치하므로,
기대 실점 계산도 신뢰할 수 있다.

### 어블레이션

한 번에 한 요소만 바꾸고 나머지 조건은 동일하게 유지했다.

| 구성 | log-loss | 제안 대비 | macro AUC | 정확도 |
|---|---|---|---|---|
| **제안 모델** | **1.1259** | — | **0.8410** | 57.48% |
| 맥락 스킵 연결 제거 | 1.1423 | **+0.0164** | 0.8364 | 56.91% |
| 시퀀스 길이 1 | 1.1302 | +0.0043 | 0.8393 | 57.36% |
| 마지막 토큰 풀링 | 1.1269 | +0.0010 | 0.8400 | 57.42% |
| 상태 임베딩 제거 | 1.1244 | −0.0015 | 0.8412 | 57.53% |

**① 맥락 스킵 연결이 기여한다.** 제거 시 log-loss +0.0164로 표에서 가장 큰 효과이며,
유일하게 노이즈 범위 밖으로 보이는 차이다. 이 프로젝트의 핵심 가설이 공정한 비교
하에서 지지됐다.

**② 시퀀스 자체의 기여는 작다.** 직전 투구 정보를 완전히 제거해도(`시퀀스 길이 1`)
차이가 +0.0043 에 그친다. 스킵 연결 효과의 약 1/4 수준이다. 예측력의 대부분은
그 공 자체의 물리량과 현재 상황·타자 특성에서 나온다.
**"투구 배합의 시계열 맥락이 결정적"이라는 처음의 전제는 이 데이터에서 강하게
지지되지 않는다.** 셋업 피치 최적화 효과가 최종구 최적화보다 작았던
Takamido & Nakamoto (2026) 의 보고와도 방향이 일치한다.

**③ 상태 임베딩은 효과가 없다.** 맥락 경로의 이득은 이산 상태 임베딩이 아니라
연속 맥락 피처, 특히 타자의 직전 시즌 성적에서 나오는 것으로 보인다.

### 희귀 클래스에 대해

안타 계열(단타·2루타·3루타·홈런)의 **재현율이 0**이다. 사전 확률이 1~4%인 클래스는
argmax 에서 최상위가 되지 못하기 때문이며, macro F1 이 낮은 것도 대부분 이 때문이다.
다만 같은 클래스들의 **AUC 는 0.785~0.835 로 순위 매기기는 정상**이다.

이는 의도한 맞바꿈이다. 재현율을 올리려면 재가중이 필요한데 그러면 캘리브레이션이
깨진다. 추천 엔진은 argmax 가 아니라 확률 분포 전체를 적분하므로 이쪽을 택했다.

### 한계

- **단일 시드 실행.** ①의 차이는 노이즈 밖으로 보이나 ②③의 차이(0.001~0.004)는
  재현 실험 없이 결론짓기 어렵다
- **학습 예산 미포화.** 검증 log-loss 의 최저값이 마지막 에폭에서 관측됐다.
  조기 종료가 아니라 에폭 상한에 걸린 것이므로 개선 여지가 남아 있다
- **추천기 자체는 미검증.** 결과 예측 모델은 홀드아웃에서 평가했으나, 추천 로직이
  실제로 더 나은 선택을 하는지는 반사실 평가로 따로 확인해야 한다

## 개정 내역

> 이 저장소는 초기 버전의 전면 재작업본이다. 초기 버전은 검증 정확도 **67.52%** 를
> 보고했으나, 재현 과정에서 그 수치가 **미래 정보 누수로 만들어진 값**임이 확인됐다.

<details>
<summary><b>무엇이 잘못됐고 어떻게 고쳤나 (펼치기)</b></summary>

### 1. 시퀀스가 시간 역순이었다

Statcast 원본은 역시간순으로 제공된다. 한 타석 안에서 `pitch_number` 가 7, 6, 5 … 1
로 내려간다. 초기 코드에는 정렬이 없었다.

```python
grouped = df.groupby('batter')        # 역순 그대로 유지됨
sequences.append(data[i : i+8])
targets.append(target_vals[i+7])      # 윈도우의 '마지막' = 시간상 가장 과거
```

결과적으로 **나중에 던져진 7개의 공으로 그보다 먼저 던져진 1개 공의 결과를 맞히는
문제**를 풀고 있었다. 볼카운트가 모든 타임스텝에 있었으므로 타깃 다음 투구의 카운트만
비교하면 정답을 직접 읽을 수 있었다 — 볼이 1 늘었으면 볼, 스트라이크가 1 늘었으면
스트라이크. 전체의 절반을 넘는 두 클래스가 입력에서 관측 가능했다.

**수정** — 시간순 정렬, 시퀀스를 타석 내부로 제한, 카운트를 맥락 경로로 분리해
누수 경로 자체를 제거.

### 2. 무작위 분할 + 겹치는 윈도우

보고서에는 "시간 순서에 따라 8:2 분할"이라 적혀 있었으나 실제로는
`train_test_split(..., stratify=y)` — 셔플 분할이었다. stride 2 슬라이딩이라
`[i..i+7]` 과 `[i+2..i+9]` 가 8개 중 6개를 공유했다.
**수정** — 시즌 단위 분할, 검증셋도 날짜 기준으로 분리.

### 3. 불균형 이중 보정으로 확률이 왜곡됨

`WeightedRandomSampler` 와 Focal Loss 를 **동시에** 썼다. 출력 확률이 균등화된
분포를 가리키게 되어, 앱에서 `temperature = 5.0` 을 손으로 박아 가리고 있었다.
**수정** — 샘플러 제거. 원인을 없애니 보정 자체가 불필요해졌다 (T = 1.070).

### 4. 데이터 범위와 결과 정의

- 시범경기 35,482구가 학습에 섞여 있었다 → `game_type == 'R'` 필터
- `triple`, `sac_fly`, GIDP, `force_out` 등 인플레이 결과 10,224구가 삭제되고 있었다
  → 매핑 재정의 (버려지는 투구 10,224 → 6)
- 2024년 3~8월만 수집돼 있었다 → 2024·2025 전체
- 인코더·스케일러를 전체 데이터에 적합 → 학습 구간 한정

### 5. 추천 점수가 수학적으로 무의미했다

```python
score = p_success - (p_fail * 1.5) - penalty
```

good/bad 두 집합이 11개 클래스를 정확히 이분하므로 `p_fail = 1 - p_success`,
따라서 `score = 2.5 * p_success - 1.5`. **가중치 1.5 는 순위에 아무 영향이 없었다.**
**수정** — 카운트 조건부 기대 실점으로 교체.

### 6. 앱의 나머지 결함

- 모델 파일 경로가 어긋나 **앱이 실행조차 되지 않았다**
- 후보 한 구를 8번 복사해 시퀀스를 만들었다 (학습은 실제 시퀀스) → 실제 타석 이력 사용
- 구종별 물리량이 리그 평균 상수였다 → 투수×구종 실측 평균
- 존 안 9칸만 후보라 유인구를 추천할 수 없었다 → 존 밖 포함 격자
- 미등록 선수를 조용히 0번 선수로 대체했다 → UNK 인덱스 + 학습 중 마스킹
- 무브먼트를 타자 좌우로 미러링한 값의 평균을 표시해 부호가 상쇄되고 있었다
  → 표시·반사실 후보에는 원본 `pfx_x`

### 초기 67.52% 와 현재 57.48% 는 비교 대상이 아니다

전자는 미래 누수를 포함하고, 카운트에서 파생되는 `strikeout`/`walk` 를 클래스로
포함하며, 시범경기가 섞여 있고, 검증셋이 학습셋과 6/8을 공유한 상태에서 측정됐다.
지표명만 같을 뿐 측정 대상이 다르다.

```

src/
├── data.py               원본 → 시퀀스 (정렬·타석경계·미러링·존 정규화)
├── prepare.py            인코더/스케일러 (학습 구간에만 적합)
├── model.py              이원 경로 Transformer
├── train.py              학습 루프 + 어블레이션 격자
├── evaluate.py           클래스별 지표·혼동행렬·캘리브레이션·temperature
├── features.py           투수 레퍼토리·카운트별 결과 가치·위치별 가치
├── profiles.py           선수/팀 집계 (경험적 베이즈 축소 적용)
├── recommend.py          후보 생성 · 기대 실점 점수 · command window
└── dashboard/            테마·차트·페이지
notebooks/
├── 01_download_statcast.ipynb   데이터 수집 (Colab)
├── 02_train.ipynb               학습 + 어블레이션 (Colab, GPU)
└── 03_build_artifacts.ipynb     테이블·프로파일·평가 (Colab, CPU)
scripts/                  로컬 실행용 CLI
models/                   학습 산출물
reports/                  최종 보고서와 그림
docs/DATA_SCHEMA.md       Statcast 컬럼 명세와 누수 주의 컬럼
```
